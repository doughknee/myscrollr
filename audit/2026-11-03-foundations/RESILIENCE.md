### R1 — P1: finalizer rejects updater targets generated by the existing Linux release build

**Resolved:** explicit deb/rpm target mappings and realistic fixture entries now pass independent hash/signature validation.

- **Location:** `desktop/scripts/release-policy.mjs:120-125`.
- **Trigger:** finish a normal all-platform draft whose `latest.json` contains `linux-x86_64-deb` or `linux-x86_64-rpm`.
- **Evidence:** the allowlist includes AppImage aliases but neither deb nor rpm; every manifest entry is checked with `assert(extensions[target])`. The existing build still runs tauri-action with all bundles and retains these manifest entries. Read-only retrieval of the actual published `desktop-v1.7.2/latest.json` confirmed both entries alongside the AppImage targets. The proof recorder already includes `.deb` and `.rpm` bytes. Windows manifest patching and the Linux signature patch preserve these keys. The new fixture contains only AppImage for Linux, so all 15 policy tests pass without exercising this production shape.
- **Impact:** a valid, signed, complete release fails verification and cannot be published through Finish Desktop Release.
- **Suggested fix:** qualify the deb/rpm updater targets with their corresponding extensions and retain hash/signature verification; add a realistic all-target manifest fixture covering both formats. Reject unexpected targets as before.
- **Confidence:** high. No signed packaging run was performed, but the existing released manifest and unchanged manifest-generation path corroborate the trigger.

### R2 — P2: publication succeeds but a failed downstream dispatch cannot be resumed through the finalizer

**Resolved:** published releases are re-verified against original build evidence, existing publication is not mutated, and downstream dispatches are separate jobs. Rerun failed jobs can resume a failed dispatch without repeating successful sibling dispatch jobs. Actual downstream workflow completion remains distinct from successful dispatch.

- **Locations:** `desktop/scripts/finalize-release.mjs:11`; `.github/workflows/finish-release.yml:76-92`.
- **Trigger:** `gh release edit --draft=false` succeeds, then the Discord, KB or website workflow dispatch fails due to a network error, rate limit, permission failure or token expiry. A timeout after GitHub accepts publication has the same ambiguity.
- **Evidence:** both resolve and verify unconditionally require `draft:true`. Rerunning the failed publish job starts at verify and rejects the now-published release; rerunning the complete workflow fails resolve for the same reason. The dispatches are sequential, so one failure prevents later dispatches, potentially leaving the download snapshot stale. Independent manual dispatch of the downstream workflows exists, but the normal finalizer retry path cannot complete its own partial success.
- **Impact:** the release is public while follow-up work remains incomplete, and the advertised finish workflow cannot recover by rerun. Blindly retrying all side effects elsewhere also risks duplicate announcements.
- **Suggested fix:** separate the immutable verification/publication boundary from recoverable side effects. Give already-published, previously verified releases a constrained resume path, or move side effects to independently retryable jobs with preserved verification evidence and idempotency/completion tracking. Never re-upload binaries or re-run signing merely to retry effects.
- **Confidence:** high, direct control-flow evidence. No external mutation was used to reproduce.

### R4 — P2: retrying a Windows build after staging succeeds can conflict with its existing artifact

**Resolved:** Windows staging and per-platform proof uploads both set `overwrite:true` under the shared serialized build/finalizer lock. Windows staging now matches the proof's 30-day retention. `docs/DESKTOP_RELEASES.md:66-75` explains failed-jobs retry, the duplicate-announcement risk of rerun-all, and using a fresh candidate after proof expiry. The documentation also separates downstream dispatch from eventual completion.

- **Location:** `.github/workflows/desktop-release.yml:448-452`, before the new proof recording/upload at lines 558-573.
- **Trigger:** Windows staged artifacts upload successfully, then recording or uploading the proof fails (for example a network failure during proof upload).
