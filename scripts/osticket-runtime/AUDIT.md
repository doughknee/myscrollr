# Direct support request evidence (SCROLLR-395)

The existing nginx server sends fixed-field events over a local Unix datagram socket to a PHP CLI collector. HTTP does not wait for the collector or its storage. No new service, external processor, paid storage or application database migration is required. The collector runs as uid 65534, separately from the application's uid 80. It uses the already installed SQLite extension.

## Trust and privacy

Only the exact addresses returned by Docker DNS for `coolify-proxy` are trusted peers; they refresh every minute. For those peers, use the **rightmost** valid X-Forwarded-For address appended by Traefik, never the caller's leftmost address. The deployed Traefik edge has neither `forwardedHeaders.insecure` nor public trusted forwarding ranges enabled. Verify this prerequisite and run the public forged-header comparison after every proxy configuration change. Direct peers ignore forwarding headers. Missing/invalid forwarding from a trusted proxy drops evidence with a bounded warning. An unresolved proxy is reported in health and causes direct-peer records; do not interpret the proxy hash as a visitor identity.

Raw peer/forwarding values exist only in the local socket message. On disk, the source is HMAC-SHA256 over a fixed domain separator, UTC day and canonical binary IP, using a random 32-byte key kept outside the webroot. Hashes correlate a source for one day, not an individual, account or device. The source key and records are not readable by PHP-FPM or served over HTTP. There is no authenticated actor ID or customer association.

Rows contain hour, daily source hash, source kind, fixed route category, bounded method, response status, count and first/last times. They contain no concrete URI, query, signature, cookie, email, user agent, body or uploaded bytes. Nginx's new server-level access destination replaces inherited raw access logging. Its error messages use the same transient socket with a different tag, and are discarded rather than retaining potentially sensitive request text. Collector warnings are fixed strings with no exception content. Existing historical logs are preserved separately during deployment, not copied into the audit store.

## Storage and availability

Bind-mount the dedicated host directory `security-audit` under the existing Coolify service directory at `/var/lib/scrollr-support-audit`. The directory is uid 65534, mode 0700; files are mode 0600. There is one SQLite database per UTC day. Each is capped at 10,000 distinct aggregate rows and 16 MiB; repeats still increment existing rows at the row cap. Thirty-day retention runs at startup/day rollover, retaining the current day and the previous 30 UTC dates (at most 31 files, 496 MiB of database pages plus a transient rollback journal). Typical usage is much smaller. No raw events are persisted.

This is **best-effort**, not a lossless request log. Datagram queue overflow, collector restart, disk failure, invalid forwarding, or the daily cap can lose evidence. The application remains available when collection fails. The existing runtime entrypoint restarts the collector after five seconds. `health.json` reports the most recent process's recorded/dropped counters, proxy-resolution state and update time; counters reset on restart and are not a historical completeness guarantee. Inspect `[SupportAudit]` warnings and stale health, as well as nginx socket-delivery failures. Data that never reached the socket cannot be counted by the collector. Traffic rejected at the external edge is outside this logger. Old missing history cannot be reconstructed.

## Build, verification and deployment

Build `Dockerfile.security` as `scrollr/osticket-runtime:8.2.35-security2` on the existing support host. PHP remains 8.2.35 and the SCROLLR-394 raster validation stays enabled. Run `security-audit.test.php`, `inline-image.test.php`, and `python3 security-audit.integration.py` on the host (Docker required, isolated container `scrollr395-test`, loopback port 18995 must be free). The integration test mounts only a synthetic support fixture and scratch audit directory, never production ticket data. It checks nginx route normalization, secret redaction, large request-body handling, storage permissions, container replacement and collector outage. It does not send email or create real tickets.

Back up generated compose and saved Coolify service configuration privately. Preserve current source/image rollback backup from SCROLLR-394. Add only the audit bind mount, update image in both saved and generated configuration, and recreate only osTicket. Confirm normal support form/staff login, authenticated read-only ticket access, actual screenshot uploads through the existing draft endpoint, and public forged X-Forwarded-For requests producing the same daily source hash. Replace the osTicket container again and verify existing audit rows remain. Keep all tickets and customer attachments intact.

Rollback: return both saved and generated image to `scrollr/osticket-runtime:8.2.35-security1` and restore the previous compose. No application source/schema reversal is needed for SCROLLR-395; inline image protection remains. Keep the audit directory and backups for evidence. Never delete the data volumes. Do not display the key, raw logs or real customer content in deployment output.
